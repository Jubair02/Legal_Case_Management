# CURRENT SYSTEM AUDIT

**Project:** AinSheba (আইনসেবা) — Legal Case Management, Bangladesh
**Audit date:** 2026-09-10
**Method:** Direct source inspection — Prisma schema, all 35 route handlers, auth/permissions/rate-limit/uploads/outbound/reminders/scheduler/dates/validation/audit modules, Next + middleware config, 11 feature views. Workflows traced UI → API → validation → DB → response.
**Scope note:** No runtime execution, load testing or live penetration testing was performed. Findings are from code reading. Where behaviour could not be confirmed from source, it is marked **UNVERIFIED** rather than asserted.

## A. WHAT IS ALREADY GOOD

Each item below is a specific implementation verified in source, not a general impression.

### A1. Money is exact, end to end
`Invoice.amount` and `Payment.amount` are `Decimal(12,2)` in Postgres. A Prisma **result extension** in `lib/db.ts` normalises them to `number` on read, with a comment explaining that Decimal objects break plain JS arithmetic and `JSON.stringify`. Exactness lives in storage and SQL; consumers get the numeric shape they expect.

### A2. Server-authoritative financial calculation
`POST /api/payments` never trusts a client-supplied balance. Inside a single `$transaction` it re-reads the invoice, sums existing payments, computes `remaining`, and rejects any amount exceeding it. The comment names the reason: **TOCTOU** — two concurrent payments could otherwise both pass the check. Invoice status is recomputed from database values, never accepted from the client.

### A3. Invoice numbers cannot be reused
A dedicated `NumberSequence` table increments monotonically. The schema documents why neither row-counting nor `max()` is safe: deleting the newest invoice makes both go backwards, reissuing a number a client already holds on paper.

### A4. No mass assignment anywhere
Every `PATCH` handler builds an explicit `data` object field by field, each with its own validation. No handler spreads a request body into a Prisma call. Verified on cases, invoices, clients, lawyers, users, hearings, documents, notifications.

### A5. Document download is properly access-controlled
`GET /api/files/[documentId]` performs: authentication → `assertCaseReadAccess` for non-staff → an additional `sharedWithClient` gate for CLIENT → path containment via `resolveUploadPath`. It then serves with `Content-Security-Policy: default-src 'none'; sandbox`, `X-Content-Type-Options: nosniff`, and forces `attachment` disposition for any active content type. **This closes the "guess a document URL" attack completely.**

### A6. Upload validation is server-side and thorough
*(This corrects a "verify" item from the earlier informal review — it is implemented.)*
- Pre-parse `Content-Length` rejection so an oversized body is refused before `formData()` buffers it into memory
- Post-parse authoritative size check against `MAX_FILE_SIZE`
- MIME prefix allowlist (`ALLOWED_MIME_PREFIXES`)
- Explicit rejection of SVG / HTML / XHTML with a user-facing reason ("export to PDF or PNG instead")
- Filename sanitisation to `[a-z0-9-]` plus a timestamp prefix
- Write path built by `storedUploadPath`, stored **relative** to the uploads root

### A7. Path traversal is contained in exactly one place
`resolveUploadPath` is the sole translator from stored value to filesystem path. It resolves, then verifies the result sits inside the uploads root, returning `null` otherwise. It also rescues legacy absolute paths from older deployments.

### A8. Sessions are genuinely revocable
Tokens carry the `sessionVersion` they were issued with. `getSessionUser` reloads the user on every request and rejects the token when the version no longer matches. A password change increments it, invalidating every other device immediately — and `change-password` re-issues the caller's cookie so their own session survives.

### A9. Brute-force protection survives horizontal scaling
`LoginAttempt` rows live in the database, not process memory, with two buckets per attempt: `IP+email`, and `email` alone as a backstop against a rotated `X-Forwarded-For`. The schema comment records why: an in-memory Map multiplied the real allowance by the replica count and reset on every deploy.

### A10. User enumeration is resisted
Login compares against a fixed `DUMMY_HASH` when the email does not exist, keeping response timing constant, and uses `timingSafeEqual` for the real comparison.

### A11. No public signup — no role-escalation surface
There is **no registration endpoint**. Users are provisioned by ADMIN via `POST /api/users`, where `role` is validated through `requireEnum` against the `ROLES` allowlist. The entire class of "user self-selects ADMIN at signup" vulnerability does not exist here.

### A12. Complete, append-only audit trail
`AuditLog` records actor id/name/role, action, entity type/id/label, a human summary, and a JSON field-level diff. Indexed on `createdAt`, `action`, `actorId`, and `(entityType, entityId)`. No update or delete endpoint exists for it. Password material is explicitly never audited.

### A13. Timezone handled as day-keys, not timestamps
Relative dates and reminder windows compare `Asia/Dhaka` **day keys** rather than epoch values. A date-only hearing recorded for today therefore never reads as already past — closing the bug class that would cause a missed hearing.

### A14. Security headers are configured deliberately
CSP, HSTS with preload (production only), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and `frame-ancestors 'none'` unless the embedding flag is set. Production boot **refuses to start** without `AUTH_SECRET` rather than silently using a development key.

### A15. Outbound messaging is an outbox, not fire-and-forget
Every message is persisted to `OutboundMessage` before dispatch, with a unique `dedupeKey`. With no provider configured, messages are marked `SIMULATED` so a chamber can review exact wording before going live. Enqueueing is best-effort and never breaks the business flow.

### A16. Reminder sweep is idempotent
Unique dedupe keys per hearing/day/channel plus unread-dedupe in `notifyUsers` mean repeated runs are safe and cheap.

### A17. Database integrity is real
Postgres enums (migrated from strings, with the schema documenting that text columns silently accepted typos), foreign keys on every relation, unique constraints on `caseNumber` / `invoiceNumber` / `email` / `dedupeKey`, and indexes on the columns actually queried.

### A18. Health endpoint that leaks nothing
Environment variables reported as presence booleans; database failures as Prisma error codes (`P1001`, `P1000`, `P2021`) rather than messages, which would carry the connection host.

### A19. Bilingual as architecture
~2,500 dictionary lines across EN and BN, with enum labels derived by key so domain values translate too, and a serif stack falling through to a Bengali webfont per glyph.

### A20. Coherent, responsive design system
One token file drives every surface. Shared chrome is factored (`Toolbar`, `SearchField`, `DialogHead`, `FieldGroup`, `StatCard`, `SectionCard`, `EmptyState`). Every data table has a card layout below its breakpoint. State is encoded in form as well as colour — priority edge stripes, hatched overdue segments for deuteranopia.

## B. WHAT IS PARTIALLY IMPLEMENTED

### B1. Pagination — server-side exists, UI does not use it
`parsePagination` / `okPaged` are implemented and every list endpoint is bounded, returning `meta.hasMore`. **No view consumes it.** The default ceiling is 1,000 rows and filtering happens client-side within that page. Adequate at pilot scale; wrong beyond a few thousand records.

### B2. Reports — correct but unscalable and commercially thin
`GET /api/reports` issues four **unfiltered** `findMany` calls (all cases, invoices, payments, hearings) and aggregates in JavaScript. There is no date-range parameter — figures are all-time only. Cost grows with total history, and a principal wants this quarter versus last, not a lifetime total. Both problems close together by pushing aggregation into SQL with a range.

### B3. Rate limiting — login only
Well-built for sign-in; no other endpoint is throttled, including upload and the 1,000-row list endpoints.

### B4. Validation — consistent but ad-hoc
The helpers are used uniformly and correctly. However `lib/validation.ts` contains only an email regex. There is **no phone validation** (relevant: Bangladesh mobile format `+8801XXXXXXXXX` / `01XXXXXXXXX`), no NID format check, and no schema library — so request shapes are validated imperatively per handler with no single source of truth shared with the client forms.

### B5. Notifications — solid, but delivery is one-way
Per-user, role-aware, ownership-enforced (`notification.userId !== user.id` → 403), read/unread, persisted, deduped. But the client portal is read-only: there is no way for a client to reply, so they still telephone the chamber.

### B6. Case timeline — data exists, unified view does not
`CaseUpdate` (progress notes), `Hearing` (with outcomes), `CaseDocument` and `AuditLog` all carry timestamps, but they are presented in separate tabs. There is no single merged chronological timeline of the matter.

### B7. Password hashing — sound but not future-proof
`scryptSync` with Node defaults, 16-byte salt, timing-safe comparison. Cost parameters are **implicit and not stored with the hash**, and there is no rehash-on-login. Raising the cost factor later cannot migrate existing users.

### B8. Dark mode — defined but unreachable
The complete dark token set exists in `globals.css`. No theme provider is mounted, so no user can switch to it.

### B9. Multi-tenancy — absent by design, but undocumented
There is no tenant/firm column on any table. The system is **single-organisation per deployment**. This appears intentional, but nothing in the repository states it, so it is discoverable only by reading the schema.

## C. WHAT IS INCORRECT

These are actual defects, not preferences.

### C1. `reactStrictMode: false` contradicts its own stated policy — LOW
`next.config.ts` disables Strict Mode. The adjacent comment argues *against* suppressing checks ("Type errors fail the build on purpose: two shipped crashes had both been caught by tsc and suppressed here") — yet Strict Mode, which surfaces effect and subscription bugs, is off.

### C2. In-process scheduler is wrong for every deployment target — CRITICAL
`startScheduler()` registers a `setInterval` from `instrumentation.ts`. On N replicas there are N sweeps. **On serverless there are none** — no process survives between requests. The dedupe keys absorb the duplicate case, which makes the serverless case more dangerous: the failure is *silence*, with nobody reminded of tomorrow's hearing and nothing logging an error.

### C3. Local filesystem storage is incompatible with the deployment model — CRITICAL
Documents are written under `process.cwd()/uploads`. The app ships `output: "standalone"` for self-hosting **and** detects Vercel. On Vercel the filesystem is ephemeral, so uploaded court filings disappear. With more than one instance, a file uploaded to replica A returns 404 from replica B. There is no backup path for the files — only for the rows pointing at them.

### C4. Hard deletes with cascading identity destruction — HIGH
No table has `deletedAt`. `DELETE /api/clients/[id]` and `/api/lawyers/[id]` remove the profile **and the linked `User` row**. For a legal practice this is likely a records-retention breach, and it is unrecoverable without a database restore — the audit log records that the deletion happened but cannot bring the record back.

### C5. Middleware `matcher` excludes `/uploads` — VERIFY, potentially HIGH
The middleware matcher excludes a `uploads` path segment. All *application* file access correctly goes through the authenticated `/api/files/[documentId]` route, and Next does not serve `uploads/` as a static directory by default (it is not under `public/`). **However**, if any deployment fronts the app with a web server (the repo ships a `Caddyfile`) that also serves the `uploads` directory directly, every document becomes publicly readable with no authentication. This must be explicitly verified against the production reverse-proxy configuration.

### C6. No password reset path — HIGH (operational)
Password change requires the current password. There is no reset flow, so a locked-out user needs an administrator to set one out of band — and there is no recovery at all if the sole ADMIN is the one locked out.

### C7. Seeded credentials are committed — MEDIUM
Four demo accounts with working passwords (`Admin@123`, `Lawyer@123`, `Staff@123`, `Client@123`) are in the login component. They are correctly gated behind `NODE_ENV !== "production"` plus an opt-in flag, so a production build hides the UI — **but the credentials for any deployment that ran the seeder are public in the repository.**

### C8. Zero automated tests — CRITICAL
`tests/` contains three build-verification shell scripts. There is no test runner in `package.json` and no unit, integration or E2E test in the repository — across 30,000 lines including money arithmetic, invoice status derivation, a twelve-branch permission matrix across four roles, and a scheduler.

### C9. No CSRF token; reliance on SameSite alone — MEDIUM
Session auth uses a cookie with `SameSite=Lax`. No CSRF token is issued. `Lax` blocks cross-site POST, which covers the common case, and all state-changing operations correctly use POST/PATCH/DELETE rather than GET. This is **acceptable but thin** — a `SameSite=Strict` cookie or a double-submit token would be more robust, and the Bearer fallback mode bypasses SameSite protection entirely when enabled.

## D. WHAT IS MISSING

Ordered by what a paying Bangladeshi chamber notices first.

| # | Missing feature | Consequence |
|---|---|---|
| D1 | **Limitation / statutory deadline tracking** | Hearings are tracked; the highest-consequence date in any matter is not. Missing a limitation period is professional negligence |
| D2 | **Court diary / calendar view** | Hearings are a chronological list. A practice plans on a month grid; no iCal export exists |
| D3 | **Invoice PDF generation and delivery** | An invoice that cannot be sent to a client is incomplete billing |
| D4 | **Payment gateway** | bKash/Nagad/Rocket are labels on manual entries. Nothing is verified or reconciled; clients cannot pay from the portal |
| D5 | **Order / judgment as a first-class record** | `courtOrder` is a free-text field on `Hearing`. Orders and judgments have no entity, no document linkage, no searchability |
| D6 | **Legal notice management** | A distinct pre-litigation workflow in Bangladeshi practice, entirely absent |
| D7 | **Global full-text search** | No way to find a case number, client or document from anywhere in the app |
| D8 | **Time and expense capture** | `billingType` exists but nothing records billable hours or disbursements, so hourly billing cannot be substantiated |
| D9 | **Conflict-of-interest check at intake** | No flag when an opposing party already exists as a client. A professional-conduct requirement |
| D10 | **Task / to-do management** | No task entity. "Next action" is free text on a hearing with no owner, due date or completion |
| D11 | **Document templates & versioning** | No Vakalatnama generation; each upload is an independent row with no supersession |
| D12 | **Internal vs client-visible notes** | `CaseUpdate` has one visibility. Its own dialog text says notes are "visible to the assigned team **and the client portal**" — so there is nowhere to record privileged internal strategy |
| D13 | **Report date ranges and export** | No period comparison, no CSV/PDF |
| D14 | **Two-factor authentication** | No second factor, even for ADMIN |
| D15 | **Client file export** | A client is entitled to their file; no export exists |
| D16 | **Trust / retainer accounting** | Client money held on account is not separated from fee income |
| D17 | **Bulk operations** | Everything is one record at a time — painful when a court adjourns a whole day's list |
| D18 | **Backup / restore runbook** | Neither database nor uploads have a documented, tested recovery procedure |
| D19 | **Error tracking & monitoring** | Unhandled errors reach the user as "Something went wrong" and the cause reaches only the server log. Nobody is alerted |
| D20 | **CI pipeline** | Nothing runs typecheck or lint on a change |
| D21 | **README / setup / deployment docs** | No onboarding path for a second developer or a self-hosting chamber |

## E. WHAT SHOULD **NOT** BE CHANGED

Explicitly preserve the following. Each is correct, deliberate, and carries reasoning in the source.

| Keep | Why |
|---|---|
| **`Decimal(12,2)` + the Prisma result extension** | Correct solution to a real problem. Do not "simplify" to Float |
| **`NumberSequence` invoice numbering** | Do not replace with count/max — the schema explains why both are wrong |
| **DB-backed `LoginAttempt` rate limiting** | Do not move to in-memory; that was the bug that was fixed |
| **`sessionVersion` revocation** | Rare and correct. Preserve through any auth refactor |
| **The transaction in `POST /api/payments`** | TOCTOU-safe by design. Do not decompose it |
| **`resolveUploadPath` as the single path translator** | The one containment choke point. Keep it single |
| **File-download CSP + sandbox + forced attachment** | Well-reasoned defence against stored-XSS via uploads |
| **Server-side upload MIME/size/active-content checks** | Complete. Do not relax to accept SVG |
| **Dhaka day-key date comparison** | Do not "simplify" to timestamp maths |
| **Explicit per-field `data` construction in PATCH handlers** | Verbose on purpose; prevents mass assignment |
| **Append-only `AuditLog` with no mutation endpoints** | Keep it non-editable |
| **Outbound outbox + `SIMULATED` mode** | Honest about what is and is not connected. Do not fake a live gateway |
| **Middleware documented as UX-not-security** | The comment is correct. Do not move authorization into the edge |
| **No public signup** | Admin provisioning is the right model for chamber software |
| **`AUTH_SECRET` hard failure in production** | Do not add a fallback key |
| **Health endpoint's leak-free reporting** | Do not "improve" it by returning messages |
| **The chamber design system and its tokens** | Coherent and complete; changes should extend, not replace |
| **Bilingual EN/BN dictionary structure** | Flat dot-keys with derived enum labels works well |
| **The in-code "why" comments** | The single best asset for onboarding. Preserve them through refactors |

## SUMMARY

The system divides cleanly. **Domain and security logic is strong** — verifiably more careful than typical for a first system, with several fixes present that only appear after someone has thought adversarially. **Infrastructure and process are prototype-grade** — no tests, no CI, no backups, no monitoring, ephemeral file storage, and a scheduler that cannot survive its own deployment targets.

Nothing in section A needs rebuilding. The work is in C2, C3 and C8 first, then the D-list — and in deciding, deliberately, whether this stays a single-organisation product.
